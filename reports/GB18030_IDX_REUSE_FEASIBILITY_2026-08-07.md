# GB18030 对齐与 idx11 复用可行性判定（2026-08-07）

## 问题

CNBE-32 的 11 位字形索引字段 `idx` 已在字段语义冻结 v1.1 中标记弃用。询问是否可以用该空置字段承载 GB18030 对齐信息。

## 实测数据

对 `data/cnbe_catalog_fixed.csv.gz` 97,686 行用 Python `gb18030` codec 实测：

| 指标 | 结果 |
|---|---:|
| 总字符 | 97,686 |
| GB18030 可编码 | 97,686 |
| 2 字节区 | 20,954 |
| 4 字节区 | 76,732 |
| 唯一 GB18030 指针 | 91,061 |
| 重复指针字符数 | 6,625 |
| 最大指针 | 329,207 |
| 指针所需位宽 | 19 bit |
| 全量序号所需位宽 | 17 bit |
| 指针落在 11 bit 内的字符 | 2,048 |

## 结论

**直接复用 `idx` 的 11 位承载 GB18030 编码不可行，也不建议作为“对齐”字段。**

原因：

1. 容量不足：GB18030 指针最大 329,207，需要 19 bit；全量 97,686 字符的连续序号需要 17 bit；11 bit 最多 2,048。
2. 非唯一键：实测 6,625 个字符存在重复 GB18030 指针，指针不能作为字符级唯一标识。
3. 语义污染：`idx` 已冻结为 deprecated，v1.1 明确 Unicode 是唯一标识、v1.2 移除该列；复垦会破坏 golden vectors、RISC-V skill table、数据库与测试的一致性。
4. 治理原则：CNBE-32 不应因位宽压力削弱证据语义；GB18030 是映射层问题，不是结构字段问题。

## 正确路径

GB18030 对齐应走独立双向映射层：

```text
Unicode（唯一标识）
  -> CNBE32 结构层（不携带 GB18030 编码）
  -> gb18030_map（unicode / char / gb18030_hex / pointer / source / status）
```

建议字段：

```text
gb18030_hex: 实际字节序列，如 0x96329935
gb18030_pointer: 线性指针（19 bit 范围内）
source: 权威映射表版本
status: MAPPED / CONFLICT / MISSING
```

若未来希望在编码内部携带对齐信息，应放入 CNBE64/CNBE128 的 evidence 字段或新扩展位，而不是复垦 `idx`。
