# CNBE-MoE 128 专家云训练复盘（2026-08-10）

## 一、结论先行

本轮训练证明了**基础设施可以跑通**，但没有证明任何新的科学结论：

1. 没有同配置 Dense 对照，不能证明 MoE 优于 Dense；
2. 没有 Unicode 码点对照，不能证明 CNBE 优于 Unicode；
3. 没有同数据、同配置、同步数的 64/128 消融，不能证明“专家越多越好”；
4. 最终指标没有超过本地 MoE-64，继续跑 256 专家只是重复实验。

因此，当前结论不是“128 专家有效”，而是“在 24M 语料和现实现下，
增加专家数既不增加产出，又会产生可量化的算力浪费”。

## 三、可量化的“重叠专家”浪费

用 `scripts_src/analyze_moe_waste.py` 对真实 mapping_128 和语料做本地复现：

| 检查项 | 数值 |
|---|---:|
| mapping 模板数 | 6,346 |
| 每个专家承载模板数 | 1 ~ 59，均值 49.6 |
| 每个专家承载语料 token | 164,386 ~ 531,310 |
| 单 step 实际路由行数 | 8,192 × 2 = 16,384 |
| 向量化实现分配槽位 | 128 × 538 = 68,864 |
| 填充浪费倍数 | 68,864 / 16,384 ≈ **4.2x** |
| 8 层共享同一路由的专家-上下文槽位 | 128（理论上限 128 × 8 = 1,024） |

浪费来源有三个：

1. **Top-2 第二专家无语义依据**：`route()` 中第二专家是 `(primary + 1) % E`，
   只是相邻编号，不是语义分工；
2. **8 层共用同一路由**：同一 token 在每一层命中同一对专家，
   专家角色在层间完全重叠；
3. **向量化 grouped GEMM 全专家 padding**：每层都按最大桶长度计算全部
   128 个专家，即使很多专家只有几十个 token，填充量约 4.2x。

结论：当前“MoE”本质是**字段哈希桶 + 相邻专家补位**，不是专家分工；
增加专家数只会线性放大参数、显存和 padding 浪费。

## 四、根因

1. **目标漂移**：把“验证 CNBE 编码结构可计算”做成了“训练中文 MoE 模型”；
   24M 语料支撑不了模型训练，于是只能反复堆参数；
2. **缺少实验门禁**：没有先定义“这个实验回答什么问题、需要什么对照、
   什么结果会改变决策”；
3. **实现不具备真正的 MoE 语义**：硬路由不学习、不随上下文变化、
   不随层变化，专家间高度重叠。

## 五、边界（已固化到 skill）

- CNBE-MoE 只回答编码层问题：CNBE vs Unicode、硬路由 vs Dense、
  字段可预测性、跨语料泛化；
- 不把“训练更大的中文模型”当作本项目目标；
- 没有对照实验、没有停止条件、没有新增决策信息时，不上云训练；
- 语料扩量是独立立项，必须服务于编码覆盖与泛化验证，而不是“把模型跑大”。
