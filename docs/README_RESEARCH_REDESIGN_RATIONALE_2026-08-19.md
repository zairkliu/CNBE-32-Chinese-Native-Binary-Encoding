# README 研究化改版说明

日期：2026-08-19  
状态：文档治理记录

## 为什么改写

CNBE 的仓库在表示层、数据库、SDK、演示程序、模型实验和系统原型上积累了较多材料。
旧 README 的开场更像成果清单：它让读者先看到“全栈”“基础设施”等宏大表述，再去
寻找问题、方法与证据边界。这样的顺序会造成三个风险：

1. 把不同成熟度的原型误读为同一项已完成能力；
2. 把数学定义、数据质量和任务有效性误读为彼此自动成立；
3. 让来自语言文字、NLP、系统或同行评议背景的读者难以判断应如何复现或反驳项目。

本次改版不删除历史材料、实验报告或系统入口，而是改变首页的证据顺序：先给出研究
问题和兼容性边界，再定义形式对象、可证伪假设与实验阶梯，随后才列出当前证据和历史
原型。原始报告仍保留在各自目录，作为研究轨迹的一部分。

## 论文与仓库的关系

未发表论文《语言主权与数字治理：中文原生 AI 治理体系的构建路径》为项目提供了问题
意识：中文 AI 的表示、数据和知识输出需要可追溯、可治理的基础条件。仓库只吸收其中
能够转化为工程方法的原则：来源链、兼容层、公开边界和可复核性。

论文并不是 CNBE 性能、标准地位或系统价值的证据；README 不转载论文全文，也不把其
宏观政策论点化约为技术结论。CNBE 的每一项技术主张仍必须由仓库内可定位的数据、代码、
预注册协议和独立评测支持。

## 新的阅读顺序

1. **问题**：是否能建立兼容 Unicode/GB 的、可审计的汉字结构描述；
2. **对象**：Unicode 身份键与版本化 CNBE 结构特征的关系；
3. **方法**：H1--H4 的可证伪假设，以及 OCR、模型、系统三类协议；
4. **证据**：已锁定实现、探索性 pilot、进行中训练与规划工作分开报告；
5. **复现**：读者可按任务入口、数据版本、基线和验收条件复算或提出反证；
6. **愿景**：SDK、模型与系统原型只在下层证据充分后逐步扩展。

## 不改变的内容

- Unicode/GB 仍为身份和互操作基础；
- 8105、GF0017、来源分级与人工审核仍是数据治理主线；
- 既有 SDK、数据库、演示、数学性质测试和系统原型继续保留；
- 负结果、构造候选实验、未完成训练和待复核比较继续保留，并以其真实证据等级说明。

## 维护规则

此后新增 README 结论应先回答四个问题：它对应 H1--H4 中哪一项？数据与基线是否固定？
何种结果能反驳它？复现入口在哪里？若不能回答，应放入路线图或研究笔记，而不作为
首页成果陈述。
