# CNBE-32 项目定位重定义

日期：2026-08-04

## 一句话定位

CNBE-32 **不是**“面向 CJK 的一种 32 位编码格式”，而是**面向中文的完整原生编码体系**：
从机器码、指令集、操作系统，到编译/解码器、编程语言与应用的纵向基础设施。
与 CJK/Unicode 的兼容只是现有计算机和网络传输协议下的**最大公约数互操作层**，
不是项目定义。

## 为什么原表述是错误的

1. “面向 CJK 的 32 位结构编码”把项目降格为 CJK 字符集的一种映射格式；
2. CJK 只是现有 Unicode 体系中的一个字符集片段，无法代表
   “机器码 → 操作系统 → 应用”的全链路；
3. C++、Python、Rust 等编程语言，RISC-V 指令协议、编译器和解码器，
   都没有被“CJK 编码格式”覆盖；
4. 项目真实目标是让中文从字符层到指令层都拥有原生表达；
   CJK 兼容仅是互操作桥，不能解释项目价值。

## 全栈覆盖范围

| 层次 | CNBE-32 对应物 |
|---|---|
| 机器码 / 寄存器 | 32 位字段位域，天然对齐寄存器与位运算 |
| 指令集 | RISC-V 扩展：字段提取、路由查表、结构比较等原语 |
| 操作系统 | 内核 / 文件系统 / 终端的中文字符处理（kernel 层实验） |
| 编译 / 解码器 | CNBE↔Unicode/GB 双向转换、结构解码、运行时校验 |
| 编程语言 | Python SDK、C、Rust 绑定与工具链 |
| 应用 | 桌面 Demo、OCR/古籍整理、MoE 结构路由、软著材料 |

## 与 CJK/Unicode 的关系

- 兼容 = 最大公约数互操作层（现有计算机与网络协议的最小公分母）；
- 兼容 ≠ 依赖：CNBE 拥有独立的位域语义、结构字段、路由协议与硬件对齐目标；
- 长期目标：中文原生独立表示，Unicode 仅作为对外互操作接口。

## 技术支柱

1. 32 位结构字段：radix / strokes / struct / index / ext；
2. 确定性结构路由：CNBE 字段 → 专家 / 服务；
3. 可计算结构：部首、结构、笔画可查询、可比较、可路由；
4. 硬件友好：RISC-V 位运算、寄存器对齐、指令原语。

## 现状与下一步

- 已有：Python SDK、C/Rust/RISC-V 绑定、24.38M 字数据集、MoE 原型、8105 Demo；
- 下一步：端到端古籍整理工具、云 GPU 规模化验证、全栈工具链完善。
