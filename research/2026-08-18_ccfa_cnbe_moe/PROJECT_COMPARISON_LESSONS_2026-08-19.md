# 已有项目情况分析与 CNBE 项目启示

日期：2026-08-19  
定位：CNBE 不是“只做 OCR 或只做 AI”，而是以可计算结构字段为核心的完整计算层

## 1. 几个项目的情况

### 1.1 ChineseBERT

情况：在 BERT 中加入字形图像和拼音 embedding，学术贡献清晰，但通用 NLU 增益不大，且没有形成独立产品。

启示：外部特征注入容易做，但没有解决“结构信息如何成为系统底层能力”的问题。

### 1.2 Glyce

情况：用字符图像表示汉字，在部分字符级任务上有增益，但图像编码开销大，未成为主流。

启示：结构表示不能依赖高成本图像编码；可计算字段更轻、更可审计。

### 1.3 SubChar

情况：把汉字拆成 radical/stroke 子 token，在序列建模和 OOV 上有帮助，但仍是 tokenizer 层改造，不是固定二进制字段。

启示：分解方向有效，但需要更稳定的字段语义和可复现路由。

### 1.4 UnihanLM

情况：利用 Unihan 数据库做粗到细预训练，属于知识增强路线。

启示：外部知识库可提供证据，但不能替代“编码自身携带结构”的设计。

### 1.5 CNM-BERT

情况：结构 embedding 在 CLUE 上只提升约 +0.19，说明通用 NLU 不是显式结构的强受益场景。

启示：不能把通用 NLU 当作 CNBE 的主卖点。

## 2. 为什么它们都没有成为 CNBE 式方案

1. 它们都停留在模型特征层，没有进入编码、数据库、指令集、OS 和应用层；
2. 它们没有固定字段代数，不能直接做 O(1) 路由和零样本结构距离；
3. 它们没有国家标准审计，字段来源不可复现；
4. 它们没有为结构敏感任务建立专用 benchmark；
5. 它们依赖学习式表示，没有“确定性结构指纹”这一层。

## 3. 对 CNBE 的启示

### 3.1 不要用通用 NLU 证明价值

结构先验在通用 NLU 上是边际的。CNBE 的主战场是：

- 形近字消歧；
- OOV / 生僻字；
- OCR 候选重排；
- 古籍文本校勘；
- 子字符级建模；
- MoE 确定性路由。

### 3.2 要做“应用验证 + 系统能力”两条线

OCR/AI 是验证 CNBE 可用的第一个入口，但项目最终目标是：

- 固定 32-bit 结构字段；
- 可计算形态距离；
- SDK / 数据库 / 指令集 / 内核一致；
- 国家标准对齐；
- 可审计、可复现。

### 3.3 结构距离单独不够，必须进入学习式系统

首轮真实 OCR 重排显示：CNBE 距离单独使用没有全面超过 Unicode。这说明 CNBE 应作为特征进入学习式 re-ranker，并与上下文、候选分布和领域规则结合。

### 3.4 需要一个“杀手任务”

ChineseBERT/Glyce/SubChar 的共同问题是缺少不可替代的应用场景。CNBE 需要至少一个“没有 CNBE 就很难做”的任务，例如：

- 形近字/古籍 OCR 后处理；
- 生僻字跨域泛化；
- 确定性 MoE 路由；
- 手写零样本候选重排。

## 4. 项目定位

CNBE 是一个“中文结构计算层”，不是“中文 OCR 插件”，也不是“中文 LLM 编码插件”。

```text
国家标准 -> CNBE 字段 -> SDK/DB -> 模型特征/MoE路由 -> OCR/古籍/应用 -> 硬件/系统
```

OCR/AI 是当前最容易验证的入口，但最终价值在整条链的一致性。

## 5. 下一阶段实验

- 用 CNBE 字段 + 上下文训练小型 re-ranker；
- 增加 Unihan variant map baseline；
- 对比 ChineseBERT / Glyce / SubChar embedding；
- 建立“结构敏感 benchmark”而不是通用 NLU benchmark。
